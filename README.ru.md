# cc-limits

Индикатор лимитов Claude Code в терминале: 5-часовое окно и недельное, отсчёт
до сброса, отклонение от равномерного темпа и прогноз исчерпания.

Цифры настоящие. `cc-limits` читает тот же эндпоинт, которым пользуется сам
Claude Code для `/usage`, это не оценка, собранная из локальных счётчиков
токенов.

English README: [README.md](README.md)

## Как выглядит

Одноразовый вывод:

```
Лимиты Claude Code  19:05:16

 5ч    [########..........................]  24.0%  сброс 1ч 54м  откл -61%  хватит до сброса (8.5%/ч)
 7д    [######............................]  19.0%  сброс 1д 12ч 54м  откл -76%  хватит до сброса (1.0%/ч)
 Fable [..................................]   0.0% (квота 50% недели)

 неделя: Claude Code 100%
```

В статуслайне Claude Code, обновляется каждый ход:

```
> my-project  git:(main)  5ч 24% -61% 1ч 54м | 7д 19% -76% 1д 12ч 54м | 19:05
```

Как читать строку:

| Поле | Значение |
| --- | --- |
| `24.0%` | расход доступного бюджета, а это всё окно, если не задан [резерв](#общий-аккаунт-резерв-части-окна). Красится по риску, см. ниже |
| `сброс 1ч 54м` | сколько осталось до сброса окна |
| `откл -61%` | отклонение от равномерного поглощения бюджета. `0%` — идёшь ровно по темпу, `-61%` — тратишь на 61% медленнее равномерного (есть запас), `+20%` — на 20% быстрее. Зелёный при нуле и ниже, жёлтый выше |
| `хватит до сброса (8.5%/ч)` | измеренная скорость расхода и вердикт, дотянешь ли до сброса. Если прогноз говорит, что упрёшься раньше — становится красным `КОНЕЦ через 1ч 30м` |

Процент расхода красится по риску, а не по собственному уровню: красный когда
бюджет выбран (100% и выше) или прогноз говорит, что упрёшься до сброса;
жёлтый пока жжёшь быстрее равномерного темпа; иначе зелёный. Голый процент сам
по себе о риске ничего не говорит, поэтому абсолютный порог врал бы: 60% за
десять минут до сброса это запас, и жёлтый там противоречил бы отклонению
рядом.

## Общий аккаунт: резерв части окна

Если аккаунт общий и часть окна надо оставлять напарнику, эта часть
объявляется резервом. Тогда всё считается от бюджета, который реально твой:
при резерве 20% на пятичасовом окне расход 80% окна читается как `100.0%`,
а всё что выше - больше 100.

`$CLAUDE_CONFIG_DIR/cc-limits.json` (по умолчанию `~/.claude/cc-limits.json`):

```json
{
  "reserve": {
    "five_hour": 20,
    "seven_day": 0
  }
}
```

Либо на запуск: `CC_LIMITS_RESERVE_5H=20`, `CC_LIMITS_RESERVE_7D=0`. Переменные
окружения побеждают файл. По умолчанию резерва нет, и тогда проценты - сырые
проценты окна.

```
Лимиты Claude Code  19:25:20
 проценты от бюджета, 5ч: 100% = 80% окна (резерв 20%)

 5ч    [#############.....................]  37.5%  (30% окна)  сброс 1ч 34м  откл -45%  хватит до сброса (14.0%/ч)
```

Пересчёт нигде не молчаливый: в шапке написано, от какого бюджета считается,
в строке рядом стоит сырой процент окна, а в статуслайне окно помечено
звёздочкой (`5ч* 38%`). Прогноз и отклонение пересчитаны тоже, так что
`КОНЕЦ через ...` означает исчерпание твоей доли, а не окна.

Резерв влияет только на показ. `--json` остаётся сырым, история замеров тоже
пишется сырой, поэтому смена резерва не портит прошлые измерения. Битый конфиг
- жёсткая ошибка, а не молчаливый откат к нулю: тихо считать от неправильного
бюджета - ровно то, против чего эта настройка и сделана.

## Несколько аккаунтов

Токенов может быть несколько: личная подписка в Keychain и, скажем, общий
долгоживущий токен парка машин от `claude setup-token`. Окна лимитов у них
свои, поэтому аккаунты описываются в конфиге, и у каждого отдельные кэш,
история и throttle: перемешанная история превратила бы скорость расхода и
прогноз в бессмыслицу, а `429` по одному токену запирал бы запросы по другому.

```json
{
  "accounts": [
    {"name": "личный", "source": "keychain"},
    {"name": "флот", "source": "file", "path": "~/.secrets/fleet-token",
     "reserve": {"five_hour": 50}}
  ]
}
```

Откуда берётся токен - поле `source`:

| source | токен |
| --- | --- |
| `auto` | как у Claude Code: `$CLAUDE_CODE_OAUTH_TOKEN`, Keychain, `.credentials.json` |
| `keychain` | macOS Keychain, service `Claude Code-credentials` |
| `credentials` | `$CLAUDE_CONFIG_DIR/.credentials.json` |
| `env` | переменная окружения с именем из `var` |
| `file` | файл из `path`: голый токен или JSON сессии |
| `command` | stdout команды из `command` (например из менеджера секретов) |
| `token` | значение `token` прямо в конфиге |

`reserve` внутри аккаунта переопределяет общий
[резерв](#общий-аккаунт-резерв-части-окна) для этого аккаунта. Без секции
`accounts` всё как раньше: один аккаунт, прежние имена файлов кэша, никаких
подписей в выводе.

Одноразовый вывод печатает блок на аккаунт, аккаунт текущего окна помечен:

```
Лимиты Claude Code  15:46:14

 личный  (данным 14с)
 5ч    [##############....................]   40.0%  сброс 1ч 59м  откл -33%  хватит до сброса (9.2%/ч)
 7д    [###...............................]   10.0%  сброс 3д 23ч 59м  откл -77%  прогноз: мало замеров (2)

 флот  (это окно)
 проценты от бюджета, 5ч: 100% = 50% окна (резерв 50%)
 5ч    [####################..............]   60.0%  (30% окна)  сброс 1ч 59м  откл  +0%  хватит до сброса (9.0%/ч)
 7д    [#####.............................]   15.0%  сброс 3д 23ч 59м  откл -65%  прогноз: мало замеров (2)
```

### Аккаунт текущего окна

В статуслайне последним через ту же вертикальную черту стоит имя аккаунта,
которым работает именно это окно:

```
5ч 24% -61% 1ч 54м | 7д 19% -76% 1д 12ч 54м | 19:05 | флот
```

Статуслайн не видит `$CLAUDE_CODE_OAUTH_TOKEN`: Claude Code вырезает её из
окружения потомков. Поэтому токен окна читается из окружения самого процесса
`claude` - по `$CLAUDE_PID`, иначе по цепочке родителей
(`/proc/<pid>/environ` на Linux, `ps eww` на macOS). Нюанс, на который легко
наступить: `ps` показывает окружение на момент `exec`, поэтому переменной,
которую экспортировал `.zshrc`, у самого шелла не видно, а у запущенного им
`claude` - видно.

Если переменной нет нигде, окно работает сессией из Keychain, и подписывается
аккаунт с `source` `keychain`, `credentials` или `auto`. Если токен окна в
конфиге не описан, вместо имени встаёт предупреждение:

```
... | 19:05 | аккаунт ? токен этого окна в конфиге не описан
```

Это не косметика: цифры в такой строке - по другому аккаунту, а расход этого
окна не видно нигде. `cc-limits --accounts` печатает, какие аккаунты описаны
и какой из них у текущего окна.

Источники токенов опрашиваются от дешёвых к дорогим и только до первого
совпадения, а найденное соответствие запоминается на час в
`cache/cc-limits-window.json` по отпечатку токена (sha256, первые 16 символов;
самого токена там нет). Иначе `source: command` дёргал бы менеджер секретов на
каждый ход статуслайна.

## Установка

Нужен Python 3.9+ (без сторонних пакетов) и подписка Claude, залогиненная
в Claude Code.

```sh
git clone https://github.com/vetermanve/cc-limits.git
cd cc-limits
./install.sh
```

`install.sh` кладёт скрипт в `~/.local/bin/cc-limits` и печатает сниппет для
статуслайна. Или руками:

```sh
install -m 755 cc-limits ~/.local/bin/cc-limits
```

## Запуск

```sh
cc-limits                 # одноразово, из кэша если он свежий
cc-limits --force         # игнорировать кэш, спросить сервер
cc-limits --watch         # живой индикатор, обновление 120 сек (минимум 60)
cc-limits --watch 300     # ...каждые 300 сек
cc-limits --statusline    # компакт в одну строку, для статуслайна Claude Code
cc-limits --json          # сырой ответ API по аккаунту этого окна
cc-limits --json --all    # сырые ответы по всем аккаунтам
cc-limits --accounts      # какие аккаунты описаны и какой у этого окна
cc-limits --account флот  # работать только с этим аккаунтом
cc-limits --refresh       # только обновить кэш и выйти (для фона)
```

`NO_COLOR=1` выключает цвет. `CC_LIMITS_FORCE_COLOR=1` включает принудительно,
когда вывод не в TTY. `CC_LIMITS_RESERVE_5H` и `CC_LIMITS_RESERVE_7D` задают
[резерв](#общий-аккаунт-резерв-части-окна).

## Встройка в статуслайн

Добавь в свой `~/.claude/statusline-command.sh`, и индикатор будет виден
каждый ход:

```sh
limits=""
if [ -x "$HOME/.local/bin/cc-limits" ]; then
    limits=$(CC_LIMITS_FORCE_COLOR=1 "$HOME/.local/bin/cc-limits" --statusline 2>/dev/null)
    [ -n "$limits" ] && limits="  $limits"
fi

printf "%s%s" "$your_existing_prompt" "$limits"
```

Готовый пример — [examples/statusline-command.sh](examples/statusline-command.sh).
Если статуслайна ещё нет, скажи про него Claude Code:

```json
{
  "statusLine": {
    "type": "command",
    "command": "~/.claude/statusline-command.sh"
  }
}
```

`--statusline` никогда не блокируется на сети: печатает то, что лежит в кэше,
а обновление отправляет в фон. Замеренная стоимость — около 60 мс.

Последний сегмент — время, на которое сняты показания. Кэш живёт до двух минут,
а пока эндпоинт отдаёт 429, и дольше, так что без отметки непонятно, насколько
устаревшие цифры перед глазами. Она серая, пока данным меньше пяти минут,
дальше жёлтая, после пятнадцати красная.

## Как это работает

Claude Code берёт данные о лимитах из

```
GET https://api.anthropic.com/api/oauth/usage
Authorization: Bearer <accessToken>
anthropic-beta: oauth-2025-04-20
```

`cc-limits` дёргает тот же эндпоинт тем же OAuth-токеном, который ищет там же,
где и Claude Code:

1. `$CLAUDE_CODE_OAUTH_TOKEN`
2. macOS Keychain, service `Claude Code-credentials`
3. `$CLAUDE_CONFIG_DIR/.credentials.json` (по умолчанию `~/.claude/.credentials.json`)

Это поведение одного аккаунта; про несколько токенов - раздел
[Несколько аккаунтов](#несколько-аккаунтов).

Токену нужен scope `user:profile`, обычный `/login` его выдаёт. За пределы
`$CLAUDE_CONFIG_DIR/cache` ничего не пишется, токен уходит только на
`api.anthropic.com`.

В ответе лежат `five_hour` и `seven_day` с расходом и временем сброса,
недельные лимиты по моделям, разбивка на что ушла неделя и состояние
extra usage. `--json` печатает это как есть.

### Лимит запросов

У эндпоинта своё окно лимита запросов, при частом опросе он отвечает `429`.
Заголовок `Retry-After` он присылает, но доверять ему тут нельзя: когда окно
исчерпано, он продолжает отказывать, обещая повтор через нуль или одну
секунду. Буквальное исполнение такой подсказки даёт цикл мгновенных повторов.

Поэтому `cc-limits` ждёт то, что больше: подсказку сервера или свой backoff -
60 секунд на первый `429`, вдвое на каждый следующий подряд, не больше 15
минут, сброс первым успешным запросом. Срок и счётчик отказов лежат в
`$CLAUDE_CONFIG_DIR/cache/cc-limits-throttle` (у именованного аккаунта -
`cc-limits-throttle-<имя>`, счётчик отказов у каждого токена свой). Пока идёт
пауза, отдаётся кэш
с пометкой возраста, и пометка желтеет после пяти минут и краснеет после
пятнадцати: решать, сколько ещё работать, по устаревшим цифрам лимита - ровно
та ошибка, которую стоит подсветить. Отсюда же TTL кэша 120 секунд и порог
60 секунд на `--watch`.

### Прогноз

Каждое обновление дописывает замер в
`$CLAUDE_CONFIG_DIR/cache/cc-limits-history.jsonl` (у именованного аккаунта -
`cc-limits-history-<имя>.jsonl`). Скорость расхода — наклон
между самым старым и самым свежим замером внутри текущего окна.

Под прогнозом должен быть реальный интервал наблюдений, поэтому он
показывается только когда замеры покрывают хотя бы 10 минут для 5-часового
окна и 2 часа для недельного. До этого в строке стоит
`прогноз: мало замеров (N)`, а не экстраполяция недели по шести минутам
данных. По той же причине отклонение не считается в первые 2% окна, где
знаменатель близок к нулю и отношение ничего не значит.

## Ограничения

- Вывод только на русском. Слоя i18n в коде нет, патч приветствуется.
- Только аккаунты с подпиской. Эндпоинт работает по OAuth, установке на
  `ANTHROPIC_API_KEY` рассказывать нечего.
- macOS и Linux. Путь через Keychain — macOS, всё остальное падает на файл
  с credentials.
- Эндпоинт не документированный публичный API. Он может измениться без
  предупреждения, и тогда этот инструмент сломается.
- Аккаунт текущего окна определяется чтением окружения процесса `claude`.
  Начнёт Claude Code прятать токен и от своего процесса или не окажется `ps` -
  подпись аккаунта в статуслайне пропадёт, цифры останутся.

## Тесты

```sh
./tests/run.sh
```

Сети не требуют: кэш и история подкладываются фикстурой, аккаунт окна
задаётся через `CLAUDE_CODE_OAUTH_TOKEN`. Проверяются разбор конфига
accounts, раздельные файлы кэша и истории, подпись аккаунта в статуслайне и
поведение без конфига.
